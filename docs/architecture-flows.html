백엔드를 파이프라인으로 읽기

도메인은 11개지만 구조가 다른 파이프라인은 6개이며, 나머지 도메인은 이 6개의 변주다. 시스템 구성 → 요청 처리 공통 경로 → 파이프라인 6개 순으로 정리하고, 마지막에 상태 저장 위치와 장애 시 동작을 표로 덧붙였다.

다이어그램 읽는 법

고정폭 글씨는 실제 코드의 함수 · Redis 키 · 상수 이름이다. 숫자는 전부 코드에 박힌 기본값이고 추정치가 아니다. 상자 색이 뜻하는 저장소는 왼쪽 범례에 있다.

시스템 구성

요약

  • 코드는 인스턴스 3~10대 · 상태는 전부 인스턴스 밖을 전제로 쓰여 있다. 그래서 분산 잠금과 Pub/Sub 팬아웃이 존재한다.
  • 인스턴스끼리 직접 통신하지 않는다. 서로에게 할 말은 전부 Redis를 거친다.
  • 실제 라이브 데모는 그 축소판 — 한 대에서 compose로 돈다. 코드는 그대로다.
전제코드에 남은 흔적
인스턴스가 여러 대조회수 flush의 분산 잠금 · 실시간 전달의 Redis Pub/Sub 팬아웃 · 주기 잡의 배타 실행
인스턴스가 언제든 죽음모든 잠금에 TTL · 종료 시 조회수 flush와 발송 작업 드레인 · WebSocket 재연결 전제
읽기가 쓰기보다 많음writer / reader 세션 분리 · 조회수 버퍼링 · 인증 스냅샷 캐시
Redis는 없어도 서비스는 살아야 함거의 모든 Redis 경로에 fail-open 분기 (예외는 로그아웃 하나)

실제 라이브 데모 배포

위 전제를 유지한 채, 데모는 한 대에서 compose로 돈다. 관리형 서비스(ALB · RDS · ElastiCache)를 쓰지 않는 대신 HA와 자동 백업을 포기한 쇼케이스 등급이다. 코드는 바뀌지 않는다 — READER_DB_URL이 비어 있으면 writer로 폴백할 뿐이다.

판단이유
Caddy에 flush_interval -1없으면 알림 SSE가 프록시 버퍼에 갇혀 실시간이 아니게 된다
컴포즈 서브넷을 고정앱이 신뢰할 프록시 IP 대역과 어긋나면 모든 요청이 IP 하나로 수렴해 rate limit이 사이트 전체를 429로 조인다
Redis allkeys-lru조회수 버퍼처럼 TTL 없는 키가 있어서, volatile-*는 상한에 닿는 순간 쓰기가 에러로 떨어진다. 앱은 Redis 실패를 흡수하니 오래된 키를 버리는 쪽이 낫다
마이그레이션은 backend에서만worker와 동시에 돌면 Alembic 버전 테이블에서 경합한다

app/domain/ · 도메인 간 import

도메인 의존 관계

요약

  • auth · users · media 셋이 기반이다. 나머지 도메인 대부분이 이 셋을 부른다.
  • posts ↔ comments · likes는 양방향이다 — 삭제 캐스케이드와 존재 검증이 서로를 부른다.
  • 알림을 만드는 도메인은 comments와 likes 둘뿐이다.
판단이유
posts ↔ comments · likes 양방향 허용게시글 삭제가 댓글·좋아요를 한 트랜잭션에서 정리해야 하고, 반대로 댓글·좋아요는 게시글 존재·가시성을 검증해야 한다. 이벤트로 끊으면 삭제가 최종 일관성이 되어 반쯤 지워진 게시글이 보이는 창이 생긴다
알림 생성을 comments·likes에만알림을 만드는 지점이 늘어날수록 "커밋 후 발행" 규약이 새는 표면이 늘어난다. 두 곳으로 묶어 두면 규약 준수를 눈으로 확인할 수 있다
admin을 소비자로만관리 기능이 도메인 로직을 재구현하면 규칙이 두 벌이 된다. admin은 읽기와 상태 전이만 하고 판정은 각 도메인에 맡긴다

app/main.py · app/core/middleware/

요청 처리 공통 경로

요약

  • 어떤 엔드포인트든 예외 없이 같은 미들웨어 스택을 통과한다. 도메인마다 다른 건 그다음부터다.
  • 미들웨어는 나중에 등록한 것이 더 바깥이라, main.py의 등록 순서를 뒤집어 읽어야 한다.
  • rate limit이 일부러 가장 안쪽에 있다. 그래야 429가 CORS 헤더를 달고 나간다.
판단이유
rate limit을 가장 안쪽에바깥에 두면 429가 CORS 헤더 없이 나가서 브라우저가 429 대신 CORS 에러를 본다. 클라이언트가 Retry-After를 읽을 방법이 사라지고 로그 · 메트릭에도 안 잡힌다
보안 헤더 · 접근 로그 · 메트릭을 한 겹으로세 겹이면 요청마다 태스크 · 스트림 쌍을 세 번 만들고 타이머도 중복이었다. 합쳐서 할당을 1/3로 줄였다
GZip을 관측 미들웨어보다 바깥에압축 시간이 지연 측정을 오염시키지 않게

계층 구조

요약

  • 도메인 11개가 전부 같은 네 층이다. 하나만 이해하면 나머지는 읽힌다.
  • 층마다 "하면 안 되는 것"이 명확하다. 트랜잭션은 서비스만 연다.
  • 조회는 reader, 쓰기는 writer. 단 쓰기 직후 읽기는 writer로 보낸다.

이 규칙 하나가 꽤 많은 걸 결정한다. 게시글 삭제는 게시글 soft-delete + 댓글 soft-delete + 좋아요 삭제 셋을 건드리는데, 커밋 권한이 서비스에만 있으니 자연히 한 트랜잭션에 묶인다. 리포지토리가 각자 커밋할 수 있었다면 중간에 실패했을 때 반쯤 지워진 게시글이 남았을 것이다.

파이프라인 ① · POST /v1/auth/{signup,login,refresh,logout}

파이프라인 ① 인증

요약

  • access는 짧게(기본 30분) 응답 본문으로, refresh는 길게(기본 7일) HttpOnly 쿠키로 나간다. JS가 못 읽는다.
  • refresh는 쓸 때마다 새것으로 교체된다(RTR). 옛것을 다시 내밀면 거부된다.
  • 인증된 요청은 Redis 스냅샷이 히트하면 DB 왕복이 0회다.
판단이유
refresh를 HttpOnly 쿠키로본문으로 주면 JS가 읽을 수 있어 XSS 한 번에 장기 자격증명이 통째로 털린다
Redis엔 다이제스트만Redis가 유출돼도 그 값으로는 토큰을 위조할 수 없다
회전(RTR) + Lua CAS토큰이 탈취돼도 정상 사용자가 한 번 갱신하면 탈취본이 무효가 된다. 비교와 교체가 원자적이라 동시 갱신 두 건이 서로를 덮어쓰지 않는다
로그아웃은 fail-open이 아니다Redis가 없으면 블랙리스트를 못 남긴다. "로그아웃됐다"고 응답해 놓고 토큰이 살아 있는 게 더 위험하므로 차라리 실패시킨다
인증 스냅샷 캐시에 비활성 상태도 저장정지된 계정을 다음 요청부터 DB 없이 즉시 튕긴다

설계 의도

로그아웃은 Redis fail-open 원칙의 유일한 예외다. 나머지는 전부 "Redis가 죽어도 진행"인데 여기만 "Redis가 죽으면 실패"다. 일관성이 깨진 게 아니라, 보안 경계에서는 가용성보다 정확성을 택한 것이다 — "로그아웃됐습니다"라고 응답해 놓고 토큰이 살아 있는 쪽이 훨씬 위험하다.

파이프라인 ② · POST /v1/posts

파이프라인 ② 게시글 작성 (멱등성)

요약

  • 전송 버튼을 두 번 누르거나 자동 재시도가 돌면 게시글이 두 개 생긴다. 이를 방지하는 경로다.
  • 클라이언트가 X-Idempotency-Key를 보내면 서버가 결과 캐시 + 처리중 잠금 두 개로 막는다.
  • Redis가 없으면 이 방어가 통째로 빠지고 그냥 만든다(fail-open).
판단이유
잠금과 결과 캐시를 둘 다잠금만 있으면 처리가 끝난 뒤 온 재시도를 못 막고, 결과 캐시만 있으면 동시에 도착한 두 요청이 나란히 캐시 미스를 보고 둘 다 만든다
지문에 user_id를 섞음다른 사용자가 우연히 같은 키를 써도 충돌하지 않고, 남의 응답이 열리지도 않는다
재생 시 requestId만 교체본문은 처음 성공했을 때 그대로여야 같은 게시글 ID를 받고, 추적 ID는 이번 요청 것이어야 로그를 따라갈 수 있다
잠금에 TTL(기본 120초), 결과 캐시에도 TTL(기본 1시간)서버가 처리 도중 중단돼도 해당 키가 영구히 잠기지 않고, 재시도 방어는 현실적인 재시도 창에서만 유지된다

파이프라인 ③ · GET /v1/posts/{id}

파이프라인 ③ 조회수 집계

요약

  • 조회마다 UPDATE를 날리면 인기 게시글 한 행에 초당 수백 건이 몰려 같은 행에 잠금 경합이 발생해 DB가 병목이 된다.
  • 그래서 조회수는 Redis에 모았다가 기본 5분에 한 번 DB에 넣는다. 조회 경로는 쓰기 DB를 건드리지 않는다.
  • 사용자에게 보이는 값은 DB에 저장된 값 + 아직 안 들어간 값을 합친 것이다.
판단이유
RENAME으로 버퍼를 떼어냄읽고 나서 지우면 읽은 뒤 지우기 전까지 들어온 조회가 통째로 날아간다. RENAME은 원자적이라 그 순간 이후의 증가가 자동으로 새 빈 버퍼에 쌓인다
커밋 성공 후에는 절대 되돌리지 않음되돌리면 이미 DB에 반영된 값이 한 번 더 더해져 조회수가 부풀어 오른다. 그래서 뒤이은 DEL이 실패해도 그냥 둔다
분산 잠금이 루프는 모든 인스턴스에서 동시에 돈다. 잠금으로 한 대만 돌게 하고, TTL이 있어서 그 인스턴스가 죽어도 다음 주기에 다른 대가 이어받는다
중복 방지 키와 버퍼를 따로둘을 한 Lua로 묶으면 Redis Cluster에서 서로 다른 슬롯이라 실행이 거부된다
정확도를 일부 포기Redis가 죽으면 미반영 조회수는 사라진다. 의도된 손실이다 — 조회수는 몇 건 어긋나도 되고, 대신 DB 부하가 수백 분의 1이 된다. 같은 판단을 좋아요 수에는 적용하지 않았다

파이프라인 ④ · WS /v1/ws/chat · GET /v1/notifications/stream

파이프라인 ④ 실시간 전달

요약

  • WebSocket은 특정 인스턴스에 물리적으로 붙어 있는 연결이다. 1번 인스턴스는 2번에 붙은 사람의 소켓을 쥐고 있지 않다.
  • 그래서 Redis Pub/Sub이 인스턴스 사이의 전달선 역할을 한다.
  • 채팅 DM과 알림 SSE가 완전히 같은 구조다. 채널 이름만 다르다.
판단이유
로컬 전달과 발행을 병렬로같은 인스턴스 수신자는 Redis 상태와 무관하게 받는다. 병렬이라 느린 소켓 하나가 Redis 발행을 늦추지 않는다 — 지연이 합이 아니라 max
envelope에 origin을 실음Pub/Sub은 구독자 전원에게 뿌리므로 자기 메시지도 되받는다. 그대로 처리하면 두 번 간다
구독 소켓을 프로세스당 1개로연결마다 구독을 열면 동시 접속자 수만큼 Redis 연결이 필요해 풀이 마르고, 그러면 rate limit · 인증 캐시 · 조회수 버퍼가 연쇄적으로 fail-open된다
수신자 목록을 한 번에 발행DM은 상대와 본인(다른 탭)이 같은 내용을 받는다. 따로 보내면 발행 왕복과 전 인스턴스의 파싱이 두 배가 된다
리스너에 백오프 재연결리스너가 죽으면 그 인스턴스는 다른 인스턴스의 메시지를 프로세스 재시작 전까지 받지 못한다. 0.5초 → 30초로 늘려가며 계속 시도한다
유저당 소켓 상한(기본 5) · 전송 타임아웃 5초응답하지 않는 소켓 하나가 팬아웃 루프를 점유하면 그 인스턴스의 실시간 전달 전체가 멈춘다. 메시지 한도만으로는 이미 열린 연결의 트래픽만 막지 연결 수는 못 막는다

전달 보장

이 경로는 at-most-once다. 발행에 실패하면 다른 인스턴스 수신자는 그 메시지를 실시간으로 못 받는다. 대신 DB에는 남아 있어 목록을 새로 불러오면 보인다. 실시간은 부가 기능이고 진실은 DB에 있다는 구도 — 재전송 큐를 만들지 않기로 한 선택이다.

파이프라인 ⑤ 이미지 업로드

요약

  • 서버가 파일을 받아 S3에 올리면 대역폭과 메모리를 파일 크기만큼 쓴다.
  • 대신 일회용 서명 URL을 발급해 주고 클라이언트가 S3와 직접 이야기하게 한다.
  • 서버는 앞뒤로 자격 심사만 한다. 파일 바이트를 한 번도 손에 쥐지 않는다.
판단이유
검사를 승격보다 먼저순서가 뒤집혀 먼저 옮긴 뒤 거부하면 DB 행이 없는 영구 객체가 남는다. 고아 청소는 DB 행 기준이라 못 찾고, pending/ 수명 정책도 이미 벗어나 못 지운다. 어느 경로로도 회수되지 않는 객체가 남는다
승격 후에 또 확인서명 URL은 15분간 유효하다. HEAD와 승격 사이에 클라이언트가 같은 URL로 다른 파일을 덮어쓸 수 있다
DB 실패 시 승격본 삭제행 없는 객체를 남기지 않기 위한 되감기
스윕은 keyset 배치 + 삭제 성공분만 DB에서 제거실패한 이미지가 앞머리에 쌓여 뒤쪽 정상 행을 굶기지 않게 커서를 넘기고, 다음 회차에 재시도한다
주기 잡과 요청 유발 경로가 같은 잠금 키키가 갈리면 두 경로가 서로를 배제하지 못해 동시에 같은 객체를 지우려 든다

파이프라인 ⑥ · app/domain/notifications/ · app/worker/

파이프라인 ⑥ 알림

요약

  • 알림은 스스로 생기지 않는다. 댓글 · 좋아요 트랜잭션 안에서 행이 만들어진다.
  • 전달은 반드시 커밋 바깥이다. 커밋 전에 발행하면 롤백 시 실체 없는 알림만 남는다.
  • 커밋 후에는 세 갈래가 서로를 기다리지 않고 나간다.
판단이유
발행은 커밋 이후커밋 전에 쏘면 롤백 시 댓글은 없는데 알림만 남는다 — 열어도 대상이 존재하지 않는다
커밋 후 전달 실패는 되돌리지 않음DB에 알림이 남아 있어 목록을 열면 보인다. 실시간은 부가 기능이고 진실은 DB에 있다
푸시를 Celery로 오프로드SNS는 외부 I/O다. 재시도 · 백오프가 필요한데 요청 경로에서 그걸 하면 응답이 매달린다
브로커 장애 시 인라인 폴백, 단 같은 멱등 키브로커 ack가 유실돼 큐와 인라인이 둘 다 실행돼도 실제 배송은 한 번만 일어난다
enqueue에 소켓 타임아웃.delay()가 요청 경로에서 호출되므로, 죽은 브로커에 소켓이 매달리면 요청이 통째로 멈춘다
종료 시 인라인 태스크 드레인발행과 멱등 마킹 사이에서 끊기면 워커 재시도 때 이중 배송 창이 다시 열린다

의존성별 정리

장애 시 동작

기본 태도는 "가용성 > 순간 정합성"이다. 말로는 추상적이니, 무엇이 죽었을 때 코드가 어떻게 행동하는지 늘어놓는다.

무엇이 죽나코드가 하는 일사용자가 느끼는 것
Redis 전체 rate limit 통과(로그인만 메모리로 계속 셈) · 인증 캐시 미스 → DB 조회 · 조회수는 writer에 직접 +1 · 멱등성 비활성 · 크로스 인스턴스 실시간 중단 · 로그아웃은 실패 서비스는 돈다. 조금 느려지고, 다른 인스턴스에 붙은 상대와의 실시간만 끊긴다
PostgreSQL writer/readyz가 503 → 로드밸런서가 이 인스턴스를 트래픽에서 뺀다서비스 불가. 유일한 hard 의존성
reader 복제 지연쓰기 직후 읽기는 writer로 보내는 규약으로 덮는다방금 쓴 것은 제대로 보인다
S3confirm이 명확한 실패 응답을 낸다. 정리 잡은 실패분을 다음 회차에 재시도이미지 업로드만 실패. 글쓰기 · 읽기는 정상
Celery 브로커같은 멱등 키로 인라인 발송 폴백. enqueue 소켓에 타임아웃이 걸려 있어 요청이 매달리지 않는다푸시가 한 번만 간다. 재시도가 없어질 뿐
pubsub 리스너0.5초 → 30초 백오프로 재연결. 5초 이상 살아남아야 백오프를 초기화한다재연결까지 다른 인스턴스발 메시지 유실. 같은 인스턴스 안 전달은 계속됨
인스턴스 재시작/readyz로 준비된 인스턴스에만 트래픽. 종료 시 조회수 flush · 인라인 발송을 드레인하고 내려간다WebSocket · SSE 재연결. 그 외 무중단
느린 SSE 클라이언트메모리 큐가 차면 신규 이벤트를 버린다실시간 알림을 놓칠 수 있다. 알림 목록에는 남아 있다
죽어가는 WebSocket전송 5초 타임아웃 후 소켓을 실제로 닫는다클라이언트가 끊김을 감지해 재연결한다

연결 종료 처리

등록만 지우고 소켓을 안 닫으면 클라이언트는 연결이 살아 있는 줄 알고 계속 보내면서 수신만 조용히 잃는다. 재연결 로직도 안 뜬다. 그래서 반드시 닫는다.

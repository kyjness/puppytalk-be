# ADR 0020 — 작업 큐: Celery에서 ARQ로 (0018의 3등급 구현 교체)

- **상태**: 채택됨 (Accepted). [ADR 0018](0018-background-work-tiers.md)의 **3등급 구현만** 대체한다
  — 등급 분리 프레임워크 자체는 0018이 그대로 정본이다.
- **관련 코드**: `app/worker/settings.py`(arq 진입점·폴링·타임아웃),
  `app/worker/jobs/notification_delivery.py`(잡 본문 + 재시도 정책),
  `app/infra/queue.py`(발행측 큐 핸들), `app/infra/redis.py::arq_redis_settings`(연결 설정 창구),
  `app/domain/notifications/service.py`(`_dispatch_sns_publish` — enqueue와 인라인 폴백)

## 맥락 (Context)

0018은 3등급(재시도가 유일한 복구)의 수단으로 Celery를 채택하면서 ARQ를 기각했다. 기각 사유가
셋이었는데, **ADR 전수 점검에서 둘이 성립하지 않는 것으로 드러났다.**

| 0018이 든 기각 사유 | 점검 결과 |
|---|---|
| 재시도를 직접 짜거나 포기해야 한다 | ARQ에 `max_tries`와 `Retry(defer=)`가 있다 — **사실이 아니다** |
| 큐 라우팅을 포기해야 한다 | `default`/`high_priority`를 정의했지만 **태스크가 하나뿐이라 나눌 대상이 없었다.** 쓰지 않는 기능을 잃는다고 적은 셈 |
| 운영 자료·트러블슈팅 사례가 얕다 | 사실 — **유일하게 유효한 사유** |

0018은 스스로 재검토 조건을 걸어 두었다 — *"태스크가 계속 하나뿐이면 재검토 대상"*. 그 조건은
이미 충족된 상태였다.

한편 Celery가 **동기**라는 사실이 이 앱에 두 겹의 비용을 만들고 있었다.

1. **워커 쪽 어댑터 105줄.** 앱은 전부 async인데 Celery 태스크는 동기 시그니처라,
   프로세스당 이벤트 루프를 손으로 유지하고 DB 풀을 시그널로 여닫는 `async_bridge`(55줄)와
   그것을 부르는 껍데기 태스크(50줄)가 필요했다. 하는 일은 통역뿐이다.
2. **요청 경로의 스레드풀 왕복.** `.delay()`가 블로킹이라 `run_in_threadpool`로 감싸야 했다
   — 알림이 생길 때마다 스레드풀 슬롯을 태운다.

정작 잡의 본체(`jobs/notification_delivery.py`)는 **이미 async**였다. 껍데기만 벗기면 되는 상태였다.

## 결정 (Decision)

**작업 큐를 ARQ로 교체한다. 외부 동작은 바꾸지 않는다.**

1. **등급 프레임워크는 건드리지 않는다.** 1·2등급(인라인 asyncio · `BackgroundTasks`)과
   lifespan 주기 루프는 그대로다. 바뀌는 것은 3등급을 무엇으로 실행하느냐뿐이다.

2. **재시도 시맨틱을 1:1로 옮긴다.** ARQ는 **그냥 예외를 올리면 재시도하지 않는다** —
   `Retry`를 올려야 한다. 이 차이를 놓치면 실패가 조용히 유실되므로 배송 실패를 명시적으로
   `Retry`로 바꾼다.

   | Celery | ARQ |
   |---|---|
   | `max_retries=3` (총 4회) | `max_tries=4` |
   | `default_retry_delay` + `retry_backoff` + `retry_jitter` | `Retry(defer=_retry_delay(job_try))` — 지수 백오프 + 지터 |
   | `NotificationDeliverySkip` → 재시도 없음 | 동일 — `Retry`를 올리지 않고 반환 |
   | `soft_time_limit=120` / `time_limit=180` | `job_timeout`(단일값) |

   지터를 유지하는 이유는 장식이 아니다 — 한 번에 실패한 배송들이 같은 초에 재시도되면
   SNS로 몰린다.

3. **폴링 간격을 2초로 둔다.** arq 기본 0.5초는 유휴에도 초당 2회 `ZRANGEBYSCORE` — 하루 17만 회다.
   같은 `compose.prod.yml`이 워커 헬스체크를 *"30초마다 Redis 왕복은 2GB에서 과하다"* 며 거부하는데,
   기본 폴링은 그보다 **60배 비싸다.** 오프라인 푸시에 sub-second SLA는 없다 — 인앱 실시간은 이미
   전달된 뒤다. `queue_read_limit`도 기본 100(= 100건 읽어 2건만 쓰고 버림)에서 4로 맞춘다.

4. **큐는 하나만 둔다.** `default`/`high_priority` 2큐는 잡이 하나라 나눌 대상이 없었다.
   쓰지 않는 라우팅 표면을 새 구현으로 옮기지 않는다. 필요해지면 그때 나눈다.

5. **연결 설정 창구를 하나로 유지한다.** ARQ는 자체 `RedisSettings`로 클라이언트를 만들어
   `redis_connection_kwargs()`를 거치지 않는 **네 번째 생성부**다. [ADR 0005](0005-resilience-no-circuit-breaker.md)가
   막으려던 "생성부마다 타임아웃이 갈린다"가 재발하지 않도록 변환을 같은 모듈
   (`arq_redis_settings`)에 가둔다.
   - `conn_timeout`은 공용 `REDIS_SOCKET_CONNECT_TIMEOUT`을 **올림**해서 넘긴다(int 타입이라
     내림하면 설정값보다 짧아져 정상 연결이 오탐으로 끊긴다).
   - `conn_retries`를 **1로, `conn_retry_delay`를 0으로** 자른다. arq 기본은 5회 × 1초 지연이다.
     이 둘은 `create_pool`에서만 읽히고 클라이언트로 전달되지 않으므로 **요청 경로에는 닿지 않는다**
     — 요청 경로 방어는 아래 결정 6이 혼자 맡는다. 여기서 자르는 것은 **부팅 지연**으로,
     죽은 Redis에서 ~17초를 ~4초로 줄인다.
   - **풀 크기를 16으로 묶는다.** arq 기본은 `None`이고 redis-py가 그것을 `2**31`로 바꾼다 —
     사실상 무제한이다. 이 레포의 다른 클라이언트는 전부 의도적으로 묶여 있고(앱 128 · 워커 멱등 4),
     큐만 예외로 두면 2GB 데모 박스에서 앱 풀 위로 끝없이 얹힌다.

6. **큐 핸들은 기동 때 만든다.** 요청 경로에서 지연 생성하면 첫 알림이 연결 시도만큼 매달린다.
   lifespan에서 한 번 만들고, 실패하면 큐 없이 간다(배송은 인라인으로 떨어진다 — fail-open).
   - `create_pool`은 `conn_timeout`(연결)만 걸고 **명령 타임아웃은 안 건다** — `RedisSettings`에
     그 필드가 없다. 그대로 두면 Redis가 *먹통*(TCP 생존, 응답 없음)일 때 `enqueue_job`이
     요청 경로에서 영원히 매달리고, 예외가 안 나니 인라인 폴백도 발동하지 않는다. 지운 Celery
     설정에는 이 가드가 있었다(`broker_transport_options={"socket_timeout": 5}`). 그래서
     풀 생성 직후 공용 `socket_timeout`을 직접 걸고, 기동 핑에 쓴 커넥션은 버린다.
   - **대가**: 기동 시 생성이 실패하면 그 프로세스는 재시작 전까지 큐 없이 돈다(Celery 시절엔
     호출마다 설정을 재평가해 브로커가 돌아오면 회복됐다). 배송은 인라인으로 이어지고
     `compose.prod.yml`이 `depends_on: redis: service_healthy`로 기동 순서를 잡으므로 수용한다.

7. **인라인 폴백은 그대로 유지한다.** `WORKER_ENABLED=false`·큐 장애 시 fire-and-forget으로
   떨어지고, 워커 잡과 **같은 멱등키·같은 `deliver_once`** 를 쓴다. 교차 경로로 둘 다 실행돼도
   배송은 한 번이다.

8. **발행측은 fail-open, 워커는 fail-fast로 갈린다.** Redis 설정이 없을 때 두 쪽의 옳은 행동이
   다르다.

   arq의 `Worker.__init__`은 `redis_settings or RedisSettings()`라, 설정을 `None`으로 넘기면
   **조용히 `localhost:6379`의 db 0에 붙는다.** db 0은 앱 데이터 키스페이스다 — 큐 키를
   분리하려고 둔 `ARQ_REDIS_DB`가 무의미해지고, 설정 누락이 "붙긴 붙었는데 엉뚱한 곳"으로
   넘어간다. **열화가 아니라 오염이다.**

   그래서 워커는 `on_startup`에서 사전 조건을 검사하고 없으면 죽는다. `Worker.main`이
   `on_startup`을 poll 루프 **전에** try/except 없이 await하므로, 잡을 하나도 집지 않고 끝난다.
   발행측(`app/infra/queue.py`)은 같은 상황에서 `None`을 반환해 인라인 폴백으로 떨어진다 —
   앱은 열화된 채로 서빙하는 것이 맞다([ADR 0005](0005-resilience-no-circuit-breaker.md)).

   > 검사를 `WorkerSettings` 클래스 본문에 두지 않은 이유: 거기서 raise하면 **Redis 없이는
   > 모듈 import 자체가 불가능**해져 단위 테스트가 워커 설정을 들여다볼 수 없게 된다.

## 트레이드오프 (Consequences)

**얻은 것**
- **어댑터 105줄 삭제.** `async_bridge`와 껍데기 태스크가 통째로 사라졌다. 후자를 감싸던
  `app/worker/tasks/` 패키지도 없앴다 — 그 분리의 명분(데코레이터 격리·순환 import 방지)이
  arq에는 존재하지 않는다.
- **요청 경로에서 `run_in_threadpool` 제거.** `enqueue_job`이 네이티브 async다.
- **위험 하나가 구조적으로 소멸.** Celery는 `task_ignore_result`를 켜지 않으면 `.delay()`가
  결과 백엔드를 pubsub subscribe 했고, 그 클라이언트는 공용 타임아웃 밖이라(기본 120s)
  먹통 Redis에서 요청이 그만큼 매달렸다. arq에는 그 구독 자체가 없다 — 설정으로 막던 것이
  구조로 사라졌다.
- **죽은 설정 정리.** 결과 백엔드(`CELERY_RESULT_*`, Redis DB 인덱스 1칸)는 읽는 코드가
  **0곳**이었고, 큐 2종은 나눌 잡이 없었다. 둘 다 함께 없어졌다.
- 의존성이 celery+kombu+billiard+vine에서 arq 하나로 줄었다.

**치른 비용**
- **redis-py가 5.x에 묶인다.** arq 0.28이 `redis[hiredis]<6`을 요구한다. 프로젝트는 상한이
  없어 6.4를 쓰고 있었으므로 다운그레이드다. 앱이 쓰는 명령은 전부 오래된 API라 동작 차이는
  없지만(단위 테스트 전량 통과로 확인), **arq가 redis 6을 지원할 때까지 상한이 따라온다.**
  `pyproject.toml`에 상한을 명시해 이 결합을 눈에 보이게 뒀다.
- **운영 자료가 얕다.** 0018이 든 유일하게 유효한 사유이며 이 결정으로 해소되지 않는다.
  대신 잡이 하나이고 실패 경로가 인라인 폴백으로 덮여 있어, 큐가 통째로 멎어도 배송은 이어진다.
- **명령 단위 타임아웃이 없다.** arq의 `RedisSettings`는 `conn_timeout`(연결)만 노출하고
  redis-py의 `socket_timeout`(명령)에 해당하는 것이 없다. 앱 풀에는 걸려 있으므로 이 공백은
  큐 경로에 한정되고, `conn_retries=1`과 기동 시 풀 생성으로 요청 경로 노출을 줄였다.
- **되짚기 비용.** 같은 문제를 두 번 결정했다. 첫 결정이 틀렸다기보다 *근거로 든 사실 확인이
  얕았다* — 대안의 기능 유무를 확인하지 않고 적었다.

## 고려한 대안 (Alternatives)

| 대안 | 기각 사유 |
|---|---|
| **Celery 유지** | 유효한 사유가 "자료가 두껍다" 하나뿐인데, 그 대가가 어댑터 105줄 + 요청 경로 스레드풀 왕복 + 결과 백엔드 위험이다. 잡이 하나인 프로젝트에서 균형이 맞지 않는다 |
| **큐를 아예 없애고 스위퍼로** | `notifications`에 `sns_delivered_at`을 두면 "아직 안 갔다"가 DB에 흔적으로 남아 큐가 불필요해진다 — [ADR 0019](0019-storage-db-write-ordering.md)가 이미지 정리에서 쓴 논거 그대로이고, 그러면 이 작업은 0018 등급표에서 3등급이 아니라 lifespan 루프 칸으로 내려간다. **다만 배송 지연이 tick 주기에 묶인다** — 이미지가 늦게 지워지는 것과 푸시가 늦게 가는 것은 사용자 체감이 다르다. 마이그레이션도 필요하다. 큐를 없애는 방향 자체는 유효하므로 **재검토 대상으로 남긴다** |
| **Dramatiq / RQ** | 0018의 판단이 그대로 유효하다. RQ는 재시도·스케줄링이 얕고 Dramatiq는 생태계가 작다. 무엇보다 **둘 다 동기**라 이 교체의 핵심 이득(어댑터 제거)이 없다 |
| **큐 2종을 arq로 그대로 옮기기** | 잡이 하나다. 쓰지 않는 라우팅 표면을 이식할 이유가 없다 |
| **재시도를 앱에서 직접 구현** | 백오프·지터·시도 횟수 관리를 손으로 짜는 것은 큐를 쓰는 이유를 없앤다 |

## 일부러 하지 않은 것 (Non-goals)

- **0018을 제자리에서 고치지 않는다.** 등급 분리 프레임워크는 그대로 옳고, 바뀐 것은 3등급의
  구현뿐이다. 무엇보다 *"내가 든 근거 셋 중 둘이 성립하지 않았다"* 는 되짚기가 이 저장소가
  남기려는 기록이다 — 원본을 덮어쓰면 그 기록이 사라진다.
- **arq cron 도입**: 조회수 flush·미디어 정리는 lifespan 루프 + 분산락으로 돈다. 0018의
  "Celery Beat를 안 쓴다"와 같은 판단이며, 수단이 바뀌었다고 결론이 바뀌지 않는다.
- **재시도 번역의 공용 데코레이터화**: "평범한 예외는 재시도되지 않는다"를 `Retry`로 바꾸는
  코드가 지금은 잡 모듈 안에 손수 들어 있다. 잡이 하나뿐이라 공용 인프라로 올리지 않는다 —
  **잡이 둘이 되는 시점이 재검토 트리거**다(그때 잡 #2가 이 함정을 스스로 밟는다).
- **잡 결과 보관**: 읽는 곳이 없다. `keep_result=0`.
- **워커 수평 확장·오토스케일**: 잡이 하나이고 데모는 단일 인스턴스다. 봉투 상한 밖.
- **redis 6 지원을 위한 arq 포크·패치**: 상한을 명시해 눈에 보이게 두고 업스트림을 기다린다.

# ADR 0018 — 백그라운드 작업: 3단 분리와 Celery 채택

- **상태**: 채택됨 (Accepted)
- **관련 코드**: `app/core/celery.py`(브로커·큐·재시도 정책),
  `app/worker/tasks/notifications.py`(유일한 Celery 태스크),
  `app/worker/async_bridge.py`(동기 Celery ↔ async 앱 어댑터),
  `app/domain/notifications/service.py`(`_dispatch_sns_publish` — 오프로드 판단과 인라인 폴백),
  `app/domain/media/service.py`(BackgroundTasks sweep), `app/main.py`(lifespan 주기 루프)

## 맥락 (Context)

요청 경로에서 떼어내야 할 일들이 성격이 제각각이다. 한 가지 수단으로 통일하면 한쪽이
과하거나 부족해진다.

- **조회수 flush** — 주기적으로 도는 정리 작업. 트리거하는 요청이 없다.
- **안 쓰는 이미지 sweep** — 실패해도 다음 주기가 같은 일을 다시 한다(자가 치유).
- **SNS 오프라인 푸시** — 외부 서비스 호출. 실패할 수 있고, 실패하면 **그 알림은 영영 유실된다.**
  사용자는 "댓글 알림을 못 받았다"는 사실조차 모른다.

세 번째만 성질이 다르다. 나머지는 "다음에 또 하면 되는" 일이지만 이건 **이번에 못 하면 끝**이다.
재시도·백오프·프로세스 사망 시 재처리가 필요하고, 그걸 요청 프로세스 안에서 만들면
상태 기계가 하나 늘어난다.

## 결정 (Decision)

**작업의 "실패 비용"에 따라 3단으로 분리하고, 재시도가 필요한 등급에만 Celery를 쓴다.**

| 등급 | 수단 | 판단 기준 | 실사용 |
|---|---|---|---|
| 1 | **인라인 asyncio** (`create_task`) | 실패해도 무방·복구 불필요 | SNS 인라인 폴백 |
| 2 | **FastAPI BackgroundTasks** | 실패해도 **다음 주기가 치유** | 안 쓰는 이미지 sweep |
| 3 | **Celery** | 실패 시 **유실이 확정**되고 재시도가 유일한 복구 | SNS 오프라인 배송 |
| — | **lifespan asyncio 루프 + 분산락** | 트리거 요청이 없는 **주기** 작업 | 조회수 flush, 미디어 정리 |

핵심은 **3등급의 진입 장벽을 높게 두는 것**이다. "무거우니까 백그라운드로"는 1·2등급으로
충분하다. 큐·워커·브로커라는 운영 표면을 늘릴 값을 하는 것은 **재시도가 정답인 작업뿐**이다.
그래서 Celery 태스크는 현재 **하나뿐이고, 그 상태가 정상**이다.

### 브로커 = 이미 있는 Redis

Celery는 쪽지를 보관할 브로커가 반드시 하나 필요하다. 새 인프라를 사지 않고 **이미 돌고 있는
Redis를 DB 인덱스로 분리해** 재사용한다(broker=`/1`, result backend=`/2`). ADR 0017의
"VM 한 대에 다 몰아 관리형 비용을 0으로" 전제와 직결된다 — SQS를 브로커로 쓰면 그 전제가 깨진다.

### 인라인 폴백은 유지한다

`CELERY_ENABLED=false`·브로커 장애 시 1등급(인라인)으로 떨어진다(fail-open, ADR 0005).
**두 경로가 같은 멱등키·같은 `deliver_once`를 쓴다** — 브로커 ack 유실로 워커와 인라인이
둘 다 실행돼도 배송은 한 번이다.

단 이 폴백은 **너무 조용하다**. 푸시가 뜨긴 뜨므로 겉보기엔 멀쩡하고, "워커가 죽었는데
아무도 모르는" 상태가 된다. 그래서 데모 배포에서도 `CELERY_ENABLED=true`를 강제한다
(`.env.prod.example`).

### 로컬에는 워커를 두지 않는다

`SNS_TOPIC_ARN`이 비면 `_dispatch_sns_publish`가 첫 줄에서 반환한다. 로컬에는 SNS 토픽도
푸시를 받을 단말도 없으므로 워커를 띄워도 **처리할 일이 0개**다. `docker-compose.yml`에
worker 서비스가 없는 것은 누락이 아니라 이 결정의 결과다(`compose.prod.yml`에는 있다).

> **실시간 전달은 이 ADR의 범위가 아니다.** 인앱 실시간(채팅 WebSocket·알림 SSE)은
> Redis Pub/Sub이며 Celery와 무관하다(ADR 0009). Celery를 통째로 제거해도 실시간 경로는
> 그대로 동작한다. Celery가 맡는 것은 **앱을 보고 있지 않은 사용자에게 보내는 푸시**뿐이다.

## 트레이드오프 (Consequences)

**얻은 것**
- 실패 시 유실이 확정되는 유일한 경로에 **재시도·지수 백오프·지터**가 선언으로 붙는다
  (`max_retries=3`, `retry_backoff`, `retry_jitter`).
- `task_acks_late=True` + `worker_prefetch_multiplier=1` — 워커가 실행 중 죽어도 다른 워커가
  다시 집는다. 요청 프로세스 안에서는 얻을 수 없는 성질이다.
- 큐 라우팅(`high_priority`)·시간 제한(soft 120s/hard 180s)으로 폭주 태스크가 격리된다.
- 브로커가 기존 Redis라 **추가 인프라 비용 0**.

**치른 비용**
- **태스크 1개에 프레임워크 하나.** 지금 규모만 보면 과하다. 이 비대칭은 의식하고 수용한다 —
  등급 판단 기준(위 표)이 있으므로 "태스크가 적다"는 남용이 없다는 뜻이지 설계 실패가 아니다.
- **동기/비동기 임피던스.** Celery는 동기 기반인데 이 앱은 async라, 태스크가 `run_async_task`로
  이벤트 루프를 빌려 쓰는 어댑터(`app/worker/async_bridge.py`)가 필요하다. 이 파일이 곧
  Celery 선택의 청구서다 — ARQ였다면 없었을 코드다.
- 배포 표면 +1(워커 컨테이너). Lightsail 2GB에서 메모리를 나눠 쓴다(ADR 0017 실측 포함).

## 고려한 대안 (Alternatives)

| 대안 | 기각 사유 |
|------|-----------|
| **인라인만**(Celery 없음) | SNS 실패 시 알림이 조용히 유실된다. 사용자는 못 받았다는 사실도 모른다 — 이 등급에 유일하게 필요한 성질이 재시도인데 그게 없다 |
| **FastAPI BackgroundTasks로 통일** | 브로커가 없어 프로세스와 수명을 같이한다. 재배포·크래시 시 진행 중 작업이 사라지고 재시도가 없다. 2등급에는 맞지만 3등급에는 부족 |
| **ARQ** | asyncio 네이티브라 `async_bridge`가 불필요했다 — 이 선택의 가장 아까운 지점이다. 다만 재시도·큐 라우팅·acks_late 상당 기능을 직접 짜거나 포기해야 하고, 운영 자료·트러블슈팅 사례가 얕다. **태스크가 계속 하나뿐이면 재검토 대상**으로 남긴다 |
| **Dramatiq / RQ** | Celery 대비 뚜렷한 이득이 없다. RQ는 재시도·스케줄링이 얕고, Dramatiq는 생태계가 작다 |
| **SQS 직접 사용**(Celery 없이) | 재시도·백오프·라우팅·결과 처리를 직접 구현해야 한다. 게다가 관리형 큐를 사는 순간 ADR 0017의 "관리형 비용 0" 전제가 깨진다 |
| **Kafka** | 이벤트 로그이지 작업 큐가 아니다. 재생·순서·다중 소비자가 요구에 없고, 브로커 운영비가 봉투에서 정당화되지 않는다(ADR 0009에서 동일 사유로 기각) |
| **Celery Beat로 주기 작업까지 통합** | 조회수 flush·미디어 정리는 이미 lifespan asyncio 루프 + 분산락으로 돈다(ADR 0007). Beat를 도입하면 스케줄러 프로세스가 하나 더 늘 뿐, 얻는 것이 없다 |

## 일부러 하지 않은 것 (Non-goals)

- **"무거운 일은 일단 Celery"** — 등급 1·2로 충분한 일을 3등급에 올리지 않는다. 큐는 공짜가
  아니라 운영 표면이다.
- **Celery Beat / 주기 스케줄러**: 위 표 참조. lifespan 루프로 충분하다.
- **결과(result backend) 소비**: 배송 태스크는 fire-and-forget이라 호출부가 결과를 기다리지
  않는다. backend는 Celery 기본 동작을 위해 두되 조회 경로를 만들지 않는다.
- **워커의 수평 확장·오토스케일**: 태스크가 하나이고 트래픽이 데모 수준이다. 봉투 상한 밖.
